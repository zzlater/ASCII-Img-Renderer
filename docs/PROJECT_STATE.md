- `src/hooks/useAsciiRenderer.ts`: the static-render hook (image path) — owns one `AsciiRenderer` instance, renders once per `[source, settings]` change via a normal effect + `setState` for metrics. **This pattern must never be copied into a live-loop hook.**
- `src/hooks/useLiveVideoRenderer.ts` (new, T4.2): the live-render hook (video path) — owns its own independent `AsciiRenderer` instance and canvas, keeps `settings` in a ref (never read from a render-body closure), and gates a `requestAnimationFrame` loop on the video element's own `play`/`pause`/`ended` events. Zero `setState` calls anywhere in the per-frame path — DEC-011 compliance was reviewed by hand-tracing every closure in the effect, not just eyeballed.
- `src/state/default-render-settings.ts`: `DEFAULT_RENDER_SETTINGS` — shared by both source types via `App.tsx`'s single settings `useState`.
- `src/components/{Header,UploadPanel,SourcePreview,AsciiOutput,ControlsPanel}.tsx` + `src/styles/app.css`: `UploadPanel` now has two sibling file inputs (image/video) and a dynamic source badge; `SourcePreview` always mounts a `<video>` element (hidden via `.is-hidden` CSS when inactive, never unmounted — this is what lets `App.tsx` read a populated video ref/element the instant the source type flips) alongside the existing `<img>` path, with native `controls` giving play/pause/seek for free.
- `src/App.tsx`: `sourceType: 'image' | 'video' | null` state selects which of `useAsciiRenderer`/`useLiveVideoRenderer` is fed a real value (both are always called, per React hook rules) and which hook's `canvasRef` reaches `AsciiOutput`. `handleImageFileSelected`/`handleVideoFileSelected` share one `requestIdRef` stale-request guard so a fast cross-type race (image pick during an in-flight video load, or vice versa) resolves last-pick-wins with the loser's resources disposed, not leaked. Switching source types disposes the inactive one's resources (bitmap+URL via existing cleanup effects; video via `disposeVideoSource`); a mount-only effect also disposes the video on `App` unmount for symmetry with the image path.

## Latest Validation

T4.1/T4.2, 2026-08-13: `npm run lint`, `npm run typecheck`, `npm test` (46/46), `npm run build` — all passed, independently confirmed by reviewer and verifier after one repair round (2 Important findings fixed: `loadVideoSource`'s one-shot listeners could be left dangling on a preempted load — fixed by also listening for `abort`; no unmount-time video disposal in `App.tsx`, asymmetric with the image path — fixed with a mirroring mount-only effect). DEC-011 compliance was the primary review focus and was confirmed clean via hand-traced closures (no `setState` anywhere in the rAF `tick()` path, `cancelAnimationFrame` provably cancels the correct scheduled frame).

**Manual video-playback verification is incomplete, and this is a known, documented gap** — not a silently-skipped step. Three video files (two synthesized via OpenCV, one copied from a genuine Windows system file, `C:\Windows\SystemApps\...\oobe-intro.mp4`) all failed to decode in this session's `claude-in-chrome` automated browser: `readyState` never advanced past `0` (`HAVE_NOTHING`). This was root-caused, not just observed: `canPlayType()` reported full codec support, a `fetch()` of the exact same bytes succeeded (200, correct content-type, correct byte length), and the failure reproduced identically with a plain HTTP-served file loaded into a brand-new `<video>` element in a fresh tab with zero app code involved. This is conclusively a media-decode limitation of this specific automated-browser environment, not an app defect. What *was* verified live: both file inputs accept files and update the UI correctly (badge, filename); switching to an image while a video load was stuck pending correctly triggered `disposeVideoSource` mid-flight with no console errors, live-exercising the cross-source-cleanup path this task's review focused on hardest. **Follow-up recommended**: a quick manual spot-check (upload a real video, confirm the ASCII canvas updates on play and freezes on pause) next time this repo is opened in a normal, non-automated browser.

## Known Risks

- **TypeScript version pin** (`~6.0.3`) blocks upgrading to TS 7 until `typescript-eslint` catches up — watch upstream.
- **Video playback not visually confirmed** (see Latest Validation above) — highest-priority item to spot-check before this is fully trusted, though the code-level DEC-011/cleanup review was unusually thorough given the stakes.
- **`getImageData` allocates a fresh buffer every `render()` call** (`canvas2d-renderer.ts`) — now genuinely live on the hot path for video (every rAF tick), not just a future concern. Worth an early profiling pass once real video playback can be confirmed, against the 30fps target (DEC-008).
- **Two independent `AsciiRenderer` instances** (one per hook) exist for the app's lifetime even though only one is ever active — not a leak, just minor duplicated offscreen-canvas overhead; only worth consolidating if profiling shows it matters (reviewer Nice-to-have, deliberately not fixed).
- **`Header`'s `renderTimeMs` freezes during video playback** — it's fed only by `useAsciiRenderer`'s (image-path) metrics state, and the live loop intentionally never touches React state per DEC-011. Diagnostics for live sources are explicitly Phase 5's (T5.2) job, not a bug now.
- **No `ErrorBoundary` anywhere in the app** (`src/main.tsx` renders `<App/>` directly) — worth considering before T4.3/T4.4 add more live-input failure modes, though camera/screen-share errors already have their own required user-visible-message handling per those tasks' acceptance criteria.
- **No `FrameSource` interface yet** (DEC-016) — still deferred; **T4.3 (webcam) is now the explicit revisit point**, since it will be the second source with genuinely similar lifecycle needs to video (a live `MediaStream`-backed element, not a static decode).
- Architectural risk to watch as T4.3/T4.4 land: `MediaStream` track cleanup on unmount/source-switch (the same category of resource-lifecycle bug T4.1/T4.2 just went through two review rounds to get right for `<video>` — apply the same rigor).
- Minor: `eslint.config.js`'s `ecmaVersion: 2020` vs. tsconfig's `target: "ES2022"` (harmless; fix opportunistically).
